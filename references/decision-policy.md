# KHA 委派决策框架（本 Skill 的工程策略，非官方强制阈值）

## A. 三道硬门槛（任何一个失败即 LOCAL 或请求明确授权）

1. **允许外发**：用户、项目 policy / NDA、许可证与数据分类允许将所需输入交给 KHA，且能最小化或脱敏。未核实则不要上传。
2. **可执行**：`kha version`、`kha whoami` 可用，账号有托管能力，已确认 CLI 版本；当前环境支持所需操作。不可用则不要凭空报成功。
3. **预算与权限**：当前请求或持久化用户政策已允许对应付费/并发/工具动作；首次付费外呼且无授权先取得许可。

## B. 可委派性评分（建议，不替代判断）

每项 0/1/2 分：

- **可分解性**：0 无独立子任务；1 可分但耦合高；2 至少 2 个可独立验收子任务。
- **增量价值**：0 比 宿主本地更慢/无质量提升；1 有有限帮助；2 对关键路径、并行取证或独立审查有显著价值。
- **数据准备成本**：0 必须完整同步私有大仓库；1 需少量受控上下文；2 可只传非敏感概要、最小文件或公开链接。
- **可验收性**：0 结果难以独立检验；1 依赖人工判断；2 可用证据、测试、diff 或可重放数据验证。

默认建议：6–8 分可考虑 KHA，4–5 分用小型只读委派试验，0–3 分本地执行。用户明确提出使用 KHA 时可跳过评分门槛，但不能跳过硬门槛。

## C. 两种云端模式比较

| 维度 | KHA-NATIVE | KHA-HOST |
|---|---|---|
| 控制者 | 云端 Coordinator 决定何时创建 Child Thread | 宿主独立创建多个 Session，控制依赖 |
| 适用 | 动态路由、角色协作、共享一个会话上下文 | 严格 DAG、分开权限、环境/输入、重试策略 |
| 通信 | 子线程通过 Coordinator 中转；不能互相直接通讯 | 宿主 显式汇总，跨 Session 只能经文件/消息重新传输 |
| 共享 | 同一 Session 的资源绑定；线程上下文独立 | 独立沙箱，不共享文件/进程 |
| 验证 | 检查 Coordinator 和目标 Child Thread 事件 | 检查每个 Session 的事件和工件 |

## D. 推荐与反例

值得考虑：独立的安全/代码审查 + 性能调查；多个公开标准/库对比；互不依赖的测试策略设计；大型资料的分区整理；多方案研究与独立交叉验证。

通常不值得：更改单个函数；简单语法错误；一次小规模代码解释；高度耦合的同一文件改动；随时需与本地开发环境交互的调试；需传未授权商业秘密的工作。

## E. 默认角色和并发

优先 **Researcher / Reviewer / Analyst** 只读角色，只有在确有需求、外发合规且授权后才采用 Builder。最初 2 个 worker、最多建议 3 个（本 Skill 的保守工作习惯）；扩大前说明为何规模增长有真实收益。不要把 KHA 配置的 1–20 个可委派 Agent 条目理解为“保证允许同时运行 20 个”。真实并发限额和价格需按账号/服务实测核查。
